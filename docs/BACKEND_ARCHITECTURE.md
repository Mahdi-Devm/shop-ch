# BACKEND_ARCHITECTURE.md

## 1. هدف این مستند

این مستند معماری بک‌اند پروژه‌ی **Flash Sale** را بر اساس الزامات فایل `01-challenge-v3-sendaaa` و ساختار فعلی پوشه‌ی `api` توضیح می‌دهد.

هدف سیستم این است که در زمان هجوم درخواست‌های خرید:

- تعداد سفارش‌های `Paid + Reserved` از موجودی اولیه‌ی ۵۰۰ عدد بیشتر نشود.
- موجودی هیچ‌وقت منفی نشود.
- وضعیت سفارش از طریق **Server-Sent Events (SSE)** به‌صورت زنده به کاربر اعلام شود.
- پیام‌ها در فاصله‌ی ذخیره در دیتابیس و انتشار در Message Broker گم نشوند.
- درخواست تکراری با یک `Idempotency-Key` برای یک کاربر سفارش تکراری نسازد.
- سرویس‌های Order و Inventory به‌صورت افقی مقیاس‌پذیر باشند.

> **مرزبندی مهم:** ساختار پوشه‌ی `api` که در حال حاضر در اختیار داریم، ساختار موجود پروژه است. الزامات چالش همچنین جداسازی سرویس‌های Order و Inventory و دیتابیس‌های مستقل آن‌ها را می‌خواهد. وجود دو ماژول در یک NestJS application به‌تنهایی معادل دو سرویس مستقل نیست. هنگام پیاده‌سازی و تحویل باید این مرز عملیاتی واقعاً برقرار باشد.

## 2. تکنولوژی‌های انتخاب‌شده

| بخش | انتخاب | توضیح |
|---|---|---|
| Backend | TypeScript + NestJS | فریم‌ورک اصلی بک‌اند |
| Database | PostgreSQL | دیتابیس رابطه‌ای با تراکنش و قفل‌گذاری |
| ORM | TypeORM | دسترسی به دیتابیس |
| Message Broker | RabbitMQ | ارتباط event-driven بین Order و Inventory |
| Message reliability | Transactional Outbox | ثبت رویداد در همان تراکنش دیتابیس و انتشار بعدی |
| Authentication | JWT (HS256) + Mock login | `POST /auth/login` موک؛ توکن با `JWT_SECRET` مشترک بین دو سرویس امضا و بررسی می‌شود |
| Validation | `class-validator` + `ValidationPipe` | اعتبارسنجی ورودی‌های DTO |
| Rate limiting | NestJS Throttler + Redis storage | محدودیت نرخ درخواست‌ها؛ شمارنده‌ها در Redis مشترک نگهداری می‌شوند تا بین Replicaها هماهنگ باشند |
| Cache / shared store | Redis | storage مشترک Throttler و در صورت نیاز کش |
| Live updates | SSE | ارسال تغییرات وضعیت سفارش به کلاینت |
| Local execution | Docker Compose | اجرای سرویس‌ها و وابستگی‌ها؛ جزئیات در `docker/DOCKER.md` |
| Frontend | Next.js (با تأیید کارفرما) | چالش Nuxt 3 را ذکر کرده؛ انتخاب Next.js با تأیید خود کارفرما انجام شده و در README ثبت می‌شود |
| Testing | ابزار تست موجود در پروژه | قراردادهای تست در بخش 12؛ ابزار نهایی باید با `package.json` تأیید شود |

### چرا RabbitMQ به‌جای Kafka؟

برای دامنه‌ی این چالش، RabbitMQ انتخاب شده است چون به صف پیام و ارتباط asynchronous میان سرویس‌ها نیاز داریم و می‌خواهیم پیچیدگی عملیاتی و زمان راه‌اندازی را در محدودیت ۴۸ ساعته کنترل کنیم. Kafka هم در متن چالش مجاز است، اما برای این پیاده‌سازی انتخاب نشده است.

RabbitMQ به‌تنهایی تضمین نمی‌کند که پیام گم نشود یا فقط یک بار پردازش شود. قابلیت اطمینان باید با Outbox، تأیید دریافت پیام، retry، مدیریت پیام‌های ناموفق و مصرف‌کننده‌ی idempotent پیاده‌سازی شود.

برای delayed delivery رزروها، روش نهایی باید با تنظیمات واقعی Broker و Docker Compose مستند شود. اگر از افزونه‌ی `x-delayed-message` استفاده می‌شود، وجود و فعال بودن آن باید در محیط اجرا تأیید شود؛ در غیر این صورت باید راهکار جایگزین قابل اتکا تعریف شود.

## 4. مسئولیت پوشه‌های اصلی

### `src/main.ts`

نقطه‌ی ورود برنامه‌ی NestJS. طبق ساختار اعلام‌شده، `ValidationPipe` سراسری در این نقطه پیکربندی می‌شود. تنظیمات واقعی bootstrap، prefix مسیرها، فیلتر خطا و Guardهای ثبت‌شده باید با کد موجود تطبیق داده شوند.

### `src/app.module.ts`

ماژول ریشه که ماژول‌های سطح برنامه و پیکربندی‌های لازم را به هم متصل می‌کند.

### `src/config/`

- `data-source.ts`: تنظیم Data Source مورد استفاده‌ی TypeORM و ابزارهای مرتبط.
- `typeorm.config.ts`: تنظیمات اتصال و رفتار TypeORM.
- `swagger.config.ts`: پیکربندی مستندات API.
- `validation-pipe.config.ts`: پیکربندی ValidationPipe.

این فایل‌ها باید تنظیمات هر سرویس را به‌درستی از environment دریافت کنند. مقادیر محرمانه نباید در سورس یا فایل‌های commit‌شده قرار گیرند.

### `src/common/`

- `@types/`: تایپ‌های مشترک.
- `abstracts/`: کلاس‌ها یا قراردادهای پایه‌ی مشترک.
- `constants/`: ثابت‌های مشترک.
- `decorators/`: دکوراتورهای مشترک.
- `filter/`: Exception Filterها.
- `modules/`: ماژول‌های زیرساختی واقعاً مشترک.
- `services/`: سرویس‌های زیرساختی مشترک.
- `utils/`: توابع عمومی و مستقل از دامنه.

کد دامنه‌ای مانند قوانین رزرو موجودی یا وضعیت سفارش نباید صرفاً برای راحتی در `common` قرار بگیرد. منطق هر دامنه باید در ماژول یا سرویس متعلق به همان دامنه بماند.

### `src/modules/`

ماژول‌های دامنه‌ای برنامه. ساختار داخلی ماژول‌ها طبق تصمیم پروژه:

```text
<module>/
├── controller/
├── service/
├── repository/
├── dto/
└── entities/
```

نام‌گذاری و حروف بزرگ/کوچک پوشه‌ها باید با conventions واقعی ریپو یکسان بماند. هر ماژول می‌تواند فایل‌های اختصاصی دیگری مانند module definition، event handler یا tests داشته باشد؛ این فایل‌ها باید متناسب با نیاز واقعی اضافه شوند.

### `src/seed/`

داده‌های اولیه‌ی مورد نیاز توسعه و تست. Seed محصول باید idempotent باشد؛ اجرای دوباره‌ی آن نباید محصول یا داده‌ی تکراری بسازد. محصول مورد انتظار چالش:

- شناسه: `11111111-1111-1111-1111-111111111111`
- موجودی اولیه: `500`

## 5. مرز سرویس‌ها و مالکیت داده

چالش دو سرویس اصلی را می‌خواهد:

### Order Service

مسئولیت‌ها:

- ارائه‌ی API عمومی خرید و سفارش.
- دریافت و بررسی `Idempotency-Key`.
- ساخت و مدیریت وضعیت سفارش.
- ثبت رویدادهای خروجی در Outbox در همان تراکنش مربوط به تغییر دیتابیس.
- انتشار وضعیت سفارش برای SSE.
- احراز هویت و اعمال Rate Limit در مسیرهای عمومی.

Order Service باید دیتابیس خودش را داشته باشد. داده‌ی سفارش و کلیدهای idempotency متعلق به این سرویس هستند.

### Inventory Service

مسئولیت‌ها:

- مالکیت موجودی محصول.
- رزرو و آزادسازی اتمیک موجودی.
- جلوگیری از منفی شدن stock و overselling.
- پردازش پیام‌های مرتبط با رزرو و آزادسازی.
- deduplication پیام‌ها با استفاده از `eventId`.
- آزاد کردن موجودی رزروهایی که در ۵ دقیقه پرداخت نشده‌اند.

Inventory Service باید دیتابیس مستقل خودش را داشته باشد. چالش هم یک PostgreSQL server با دو دیتابیس و هم دو Engine جدا را مجاز می‌داند، اما هر سرویس باید دیتابیس جداگانه داشته باشد. در این پروژه برای سادگی و بدون نیاز به اسکریپت اضافه، **دو کانتینر Postgres جدا** استفاده می‌شود: `postgres` برای Order (`order_db`) و `postgres-inventory` برای Inventory (`inventory_db`). هر سرویس فقط به دیتابیس خودش وصل می‌شود. این دو سرویس نباید برای انجام کار دامنه‌ای مستقیماً از طریق HTTP به هم درخواست بزنند؛ ارتباط دامنه‌ای باید از RabbitMQ عبور کند.

> اگر پروژه در حال حاضر فقط یک برنامه‌ی NestJS در `api` دارد، نباید با نام‌گذاری دو پوشه ادعا کنیم که دو سرویس مستقل ساخته شده‌اند. جداسازی باید در entry pointها، تنظیمات اجرا، اتصال‌های دیتابیس و Docker Compose نیز برقرار باشد.

## 6. الگوی داخلی ماژول‌ها

### Controller

- دریافت HTTP request و استخراج پارامترها، headerها و body.
- استفاده از DTOهای اعتبارسنجی‌شده.
- فراخوانی لایه‌ی service.
- تبدیل نتیجه به پاسخ مناسب API.
- نگهداری نکردن منطق تراکنش یا قوانین اصلی دامنه در Controller.

### Service

- اجرای use caseها و قوانین دامنه.
- هماهنگی بین repositoryها و اجزای دامنه‌ی همان سرویس.
- مدیریت تراکنش در مرز مناسب.
- اعمال قواعد وضعیت سفارش یا رزرو.
- پرهیز از وابستگی مستقیم به Controllerها.

### Repository

- کپسوله‌کردن عملیات persistence.
- اجرای queryهای لازم با TypeORM.
- نگهداری قفل‌گذاری دیتابیس در مسیر صحیح و قابل بررسی.
- جلوگیری از پنهان کردن قواعد concurrency پشت قفل in-memory.

### DTO

- تعریف قرارداد ورودی و خروجی API.
- استفاده از `class-validator` برای ورودی‌ها.
- رد کردن `quantity`هایی که دقیقاً برابر ۱ نیستند.

### Entities

- مدل‌سازی داده‌های متعلق به همان دیتابیس و سرویس.
- تعریف constraintهای دیتابیس مورد نیاز، از جمله unique constraint برای کلیدهای idempotency و کلیدهای deduplication، متناسب با طراحی نهایی.

## 7. Concurrency و Zero Overselling

تضمین موجودی نباید به حافظه‌ی یک process وابسته باشد. ممکن است چند Replica از Order Service و Inventory Service هم‌زمان اجرا شوند.

راهکار انتخابی باید در سطح دیتابیس یا یک سازوکار توزیع‌شده‌ی معادل عمل کند. با PostgreSQL و TypeORM، گزینه‌ای مناسب برای بررسی، تراکنش همراه با قفل ردیف مانند `SELECT ... FOR UPDATE` است. پیاده‌سازی نهایی باید نشان دهد قفل در کدام فایل و خط قرار دارد.

شرط‌های صحت:

- `stock >= 0`
- مجموع سفارش‌های `Paid + Reserved` از موجودی اولیه بیشتر نشود.
- رقابت بین درخواست‌های هم‌زمان نتواند یک موجودی را چند بار رزرو کند.
- لغو یا انقضای رزرو، موجودی را دقیقاً به اندازه‌ی رزرو مربوطه آزاد کند.
- پردازش دوباره‌ی یک پیام باعث رزرو یا آزادسازی تکراری نشود.

**مستند تحویل باید محل دقیق قفل را با قالب `file:line` اعلام کند.** این مسیر باید پس از پیاده‌سازی واقعی ثبت شود؛ نباید از قبل یا به‌صورت حدسی نوشته شود.

## 8. Idempotency، Outbox و پیام‌رسانی

### Idempotency

- کلید از header با نام `Idempotency-Key` دریافت می‌شود.
- یکتایی کلید در محدوده‌ی هر کاربر رعایت می‌شود.
- درخواست تکراری نباید سفارش جدید بسازد.
- برای تضمین در چند Replica، باید از constraint و persistence مشترک استفاده شود، نه فقط Map یا حافظه‌ی محلی.
- مدت نگهداری پیشنهادی چالش ۲۴ ساعت است؛ مقدار نهایی باید در مستندات و پیاده‌سازی یکسان باشد.

### Transactional Outbox

تغییر دیتابیس و ثبت رویداد خروجی باید در یک تراکنش دیتابیس انجام شوند. یک worker یا poller رویدادهای ثبت‌شده و منتشرنشده را به RabbitMQ ارسال می‌کند و وضعیت انتشار را ثبت می‌کند.

این روش پنجره‌ی گم‌شدن پیام در فاصله‌ی commit دیتابیس تا publish را پوشش می‌دهد، اما ممکن است پیام دوباره منتشر شود؛ به همین دلیل consumer باید idempotent باشد.

### Consumer و event deduplication

- هر رویداد باید `eventId` قابل تشخیص داشته باشد.
- consumer باید دریافت تکراری را تشخیص دهد.
- پیام پس از پردازش موفق acknowledge شود.
- خطاهای موقت باید سیاست retry مشخص داشته باشند.
- پیام‌هایی که پس از retry قابل پردازش نیستند باید به‌شکل قابل مشاهده مدیریت شوند؛ نباید بی‌صدا حذف شوند.

### Expiration

رزرو بدون پرداخت باید پس از ۵ دقیقه به وضعیت `Expired` برسد و موجودی آن آزاد شود. زمان‌بندی delayed delivery باید در انتخاب Broker و تنظیمات واقعی محیط اجرا مشخص شود. مصرف‌کننده باید در برابر تأخیر، تکرار و رسیدن پیام منقضی‌شده پس از تغییر وضعیت مقاوم باشد.

## 9. Authentication، Validation و Rate Limit

### JWT

الزام صریح چالش، استفاده از JWT Guard برای تمام مسیرهای `/api/*` است. مسیرهای عمومی و استثناها، در صورت وجود، باید صریح و محدود تعریف شوند.

طبق چالش، احراز هویت **موک** است و نیازی به ثبت‌نام، رمز واقعی یا refresh token نیست:

```text
POST /auth/login
Body: { "username": "user1", "password": "any" }
→ 200 { "access_token": "<JWT HS256>", "userId": "user1" }
```

- توکن با الگوریتم **HS256** و مقدار `JWT_SECRET` از `.env` امضا می‌شود.
- هر دو سرویس (Order و Inventory) باید همان secret را بشناسند.
- مسیر `/auth/login` عمومی است و زیر `/api/*` نیست؛ همه‌ی مسیرهای `/api/*` با JWT Guard محافظت می‌شوند.
- هدر استاندارد: `Authorization: Bearer <token>`. برای SSE قاعده‌ی جداگانه در بخش 11 آمده است.

### ValidationPipe و DTO

اعتبارسنجی ورودی‌ها باید با `class-validator` روی DTOها انجام شود. برای عملیات خرید، `quantity` باید دقیقاً برابر ۱ باشد. رفتارهایی مانند رد فیلدهای ناشناخته و تبدیل نوع‌ها باید در تنظیمات واقعی `ValidationPipe` بررسی و مستند شوند.

### Rate limiting

چالش این محدودیت‌ها را می‌خواهد:

- هر IP: `10 req/s`
- هر user: `5 req/s`
- در صورت عبور از حد: HTTP `429` همراه با `Retry-After`

محدودیت مبتنی بر user باید پس از شناسایی کاربر (بعد از JWT Guard) اعمال شود. چون سرویس چند Replica دارد، شمارنده‌های Throttler در **Redis** نگهداری می‌شوند و به حافظه‌ی محلی هر process وابسته نیستند. در پاسخ `429` هدر `Retry-After` باید برگردانده شود.

### دسترسی به Inventory

پورت Inventory نباید در `docker-compose.yml` به host منتشر شود. فقط سرویس‌های لازم برای استفاده‌ی بیرونی، از جمله Order API (از طریق gateway) و فرانت Next.js، باید از بیرون قابل دسترسی باشند. شبکه‌ی داخلی Docker و تنظیمات دسترسی باید این مرز را حفظ کنند.

### قرارداد API (مرجع چالش)

| Method و مسیر | توضیح | پاسخ‌ها |
|---|---|---|
| `POST /auth/login` | ورود موک | `200 { access_token, userId }` |
| `POST /api/orders` | ثبت سفارش؛ هدر `Idempotency-Key` (uuid v4) الزامی؛ body: `{ productId, quantity: 1 }` | `201 { orderId, status: "Pending", version: 1 }`، `409 DUPLICATE_IDEMPOTENCY_KEY`، `409 SOLD_OUT`، `429 RATE_LIMITED` (+ `Retry-After`)، `401`، `400` |
| `GET /api/orders/:id` | وضعیت سفارش | `200 { orderId, status, version, productId, quantity, createdAt }` |
| `GET /api/products/:id` | موجودی محصول | `200 { id, stock, reserved }` |
| `GET /api/orders/:id/events` | کانال زنده (SSE) | `text/event-stream`؛ هر event: `data: {"status":"Reserved","version":2}` |

وضعیت‌های سفارش: `Pending`, `Reserved`, `Paid`, `Cancelled`, `Expired`.

محصول seed: `id = 11111111-1111-1111-1111-111111111111` با `stock = 500`.

**فرمت پیام بین سرویس‌ها در RabbitMQ:**

```json
{ "eventId": "uuid", "aggregateId": "...", "version": 1, "occurredAt": "ISO-8601", "type": "...", "payload": {} }
```

`eventId` یکتا است و consumer بر اساس آن idempotent عمل می‌کند (فرض: at-least-once delivery).

## 10. مدیریت خطا

طبق ساختار اعلام‌شده، پروژه از Exception Filter سراسری استفاده می‌کند. جزئیات واقعی آن باید از کد تأیید شود.

رفتار مورد انتظار:

- خطاهای اعتبارسنجی پاسخ قابل فهم و مناسب داشته باشند.
- خطای دیتابیس یا RabbitMQ باعث crash کنترل‌نشده‌ی سرویس نشود.
- خطاهای موقت، retry امن داشته باشند.
- پیام ناموفق بی‌صدا گم نشود.
- جزئیات داخلی، stack trace و اطلاعات حساس در پاسخ عمومی افشا نشوند.
- خطاها برای عیب‌یابی در log ثبت شوند، بدون ثبت token یا داده‌های حساس.

## 11. SSE و وضعیت سفارش

صفحه‌ی سفارش باید تغییرات وضعیت را بدون refresh دریافت کند. وضعیت‌های ذکرشده در چالش عبارت‌اند از:

`Pending → Reserved → Paid / Cancelled / Expired`

**احراز هویت SSE:** مرورگر در اتصال `EventSource` هدر سفارشی نمی‌فرستد. بنابراین endpoint `GET /api/orders/:id/events` باید توکن را هم از هدر `Authorization: Bearer` و هم از query string به شکل `?token=<JWT>` بپذیرد. چون توکن در URL قرار می‌گیرد، نباید در لاگ‌ها ثبت شود.

جریان رویدادها باید بر اساس مالکیت سفارش و دسترسی کاربر کنترل شود. endpoint مربوط به SSE نباید امکان مشاهده‌ی وضعیت سفارش کاربر دیگر را فراهم کند.

در صورت قطع اتصال، رفتار reconnect و بازیابی وضعیت جاری باید مشخص باشد. SSE فقط کانال اعلان زنده است؛ منبع حقیقت وضعیت سفارش باید دیتابیس باشد.

## 12. تست‌های الزامی چالش

چالش چهار تست معنادار را به‌صراحت درخواست می‌کند:

### 12.1 Concurrency

۵۰ درخواست خرید موازی ارسال شود و اثبات شود overselling رخ نمی‌دهد. علاوه بر آن، تست چند Replica نیز باید بررسی شود؛ چالش نمونه‌ای مانند اجرای سه Replica از Order Service و ارسال ۲۰۰ درخواست موازی را مطرح می‌کند.

Assertions پیشنهادی:

- `stock >= 0`
- `count(Paid + Reserved) <= 500`
- موجودی و تعداد سفارش‌ها پس از پایان پردازش با هم سازگار باشند.

### 12.2 Idempotency

یک `Idempotency-Key` برای یک کاربر دو بار ارسال شود و دقیقاً یک سفارش ایجاد شود. تست باید persistence واقعی کلید و رفتار درخواست تکراری را بررسی کند.

### 12.3 Outbox Recovery

سناریوی crash قبل از publish شبیه‌سازی شود. پس از restart یا recovery، پیام باید منتشر و پردازش شود. طبق چالش، Mock برای شبیه‌سازی crash در این تست قابل قبول است.

### 12.4 E2E Integration

مسیر کامل زیر آزمایش شود:

`POST /orders → Inventory → SSE`

تست با Testcontainers یا `docker compose` اجرا شود و فقط به mock کردن تمام اجزای زیرساختی محدود نباشد.

### تست‌های تکمیلی پیشنهادی

- درخواست بدون JWT و JWT نامعتبر.
- Rate limit مستقل بر اساس IP و user و بررسی `Retry-After`.
- رد `quantity` غیر از ۱.
- deduplication رویداد تکراری.
- انقضای رزرو پس از ۵ دقیقه و آزاد شدن دقیق موجودی.
- رفتار قابل‌کنترل هنگام قطعی RabbitMQ یا دیتابیس.
- دسترسی کاربر به SSE فقط برای سفارش مجاز.

### Test Runner

نام ابزار تست از روی ساختار پوشه به‌تنهایی قابل تعیین نیست. پیش از نوشتن دستورهای اجرا، `package.json` و فایل‌های تنظیمات تست باید بررسی شوند. قرارداد اصلی، نتیجه‌ی تست‌هاست؛ نه انتخاب یک کتابخانه‌ی تست خاص.

## 13. Docker Compose و اجرای محلی

محیط باید با یک دستور مستندشده بالا بیاید و در شرایط مورد انتظار چالش، شروع سرویس‌ها کمتر از دو دقیقه طول بکشد. جزئیات سرویس‌ها، پورت‌ها و متغیرهای محیطی در `docker/DOCKER.md` آمده است.

**وضعیت فعلی:** `docker/compose.yml` فقط زیرساخت را بالا می‌آورد: `postgres` (Order DB)، `postgres-inventory` (Inventory DB)، `redis` و `rabbitmq`. اپ‌های NestJS و Next.js فعلاً با `pnpm` روی ماشین توسعه اجرا می‌شوند.

**پیش از تحویل:** سرویس‌های `order`، `inventory` و `web` به compose اضافه می‌شوند. `order` پورت ثابت host ندارد و جلوی Replicaهایش یک load balancer (مثلاً nginx با `proxy_buffering off` برای SSE) قرار می‌گیرد تا `docker compose up --scale order=3` کار کند. `inventory` اصلاً `ports` ندارد.

**Delayed delivery (انقضای ۵ دقیقه):** راهکار پیش‌فرض این پروژه، صف TTL به‌همراه dead-letter exchange است که به افزونه‌ی اضافه نیاز ندارد و روی ایمیج رسمی `rabbitmq` کار می‌کند. اگر به `x-delayed-message` تغییر داده شود، باید ایمیج سفارشی ساخته و این سند و `ARCHITECTURE.md` به‌روز شوند.

چک‌لیست:

- [ ] Order Service و Inventory Service مستقل اجرا می‌شوند.
- [ ] هر سرویس دیتابیس مجزا دارد (`order_db` و `inventory_db`).
- [ ] Redis برای Throttler در دسترس است.
- [ ] RabbitMQ در شبکه‌ی مورد نیاز سرویس‌ها در دسترس است.
- [ ] پورت Inventory به host منتشر نشده است.
- [ ] health check و ترتیب آمادگی وابستگی‌ها در نظر گرفته شده‌اند.
- [ ] seed محصول با شناسه‌ی ثابت و موجودی ۵۰۰ idempotent است.
- [ ] متغیرهای محیطی در `.env.example` مستند شده‌اند، `JWT_SECRET` بین دو سرویس یکسان است و secret واقعی commit نشده است.
- [ ] مسیر فایل `.env` که compose و اپ‌ها می‌خوانند مشخص و در `docker/DOCKER.md` ثبت شده است.
- [ ] `docker ps` نشان می‌دهد Inventory پورت host ندارد.
- [ ] چند Replica از Order Service بدون وابستگی به حافظه‌ی محلی کار می‌کنند.

## 14. فایل‌های مستندات تحویل

### `README.md`

باید دستور اجرای پروژه، سرویس‌ها، Broker انتخاب‌شده، دیتابیس‌ها، روش اجرای تست‌ها و بخش `AI-Usage Disclosure` را توضیح دهد.

### `ARCHITECTURE.md`

چالش برای این فایل دیاگرام Mermaid و پاسخ به این شش موضوع را می‌خواهد:

1. دیاگرام کلی سیستم.
2. راهکار جلوگیری از Dual-Write بین دیتابیس و Broker.
3. مقیاس‌پذیری افقی، جلوگیری از گلوگاه دیتابیس و محل دقیق قفل با `file:line`.
4. رویکرد امنیتی و تهدیدهای در نظر گرفته‌شده.
5. دلیل انتخاب RabbitMQ و روش Delayed Delivery.
6. Trade-offها، برنامه‌ی توسعه در صورت داشتن یک ماه زمان و استراتژی تست.

این فایل `BACKEND_ARCHITECTURE.md` ساختار و مسئولیت‌های بک‌اند را توضیح می‌دهد؛ در تحویل نهایی، `ARCHITECTURE.md` باید تصمیم‌های نهایی و محل دقیق پیاده‌سازی را نیز ثبت کند.
